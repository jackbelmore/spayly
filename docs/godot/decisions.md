# Godot port: decisions and evidence

Every research claim is untrusted until a row here cites the API dump (`docs/godot/api-dump/`, regenerate with
`godot --doctool`), a GodotSharp XML entry, a PR, or a measurement from `godot/tools/run-capture.sh`.
Engine: **Godot 4.8 dev6 mono** (`4.8.dev6.mono.official.8898c2b3d`), pinned. Fallback if a crash is the
engine: 4.7.2 stable. .NET SDK 10.0.112.

### 2. Texture streaming and forcing one texture to full resolution
- **Claim** (report 1): custom shaders need a `sampler2DStreamed` uniform type.
- **Evidence**: the string `sampler2DStreamed` does not occur in the dev6 binary, the class docs, or GodotSharp.xml.
  The binary carries shader defines `TEXTURE_STREAMING`, `TEXTURE_STREAMING_DEPTH_PREPASS`,
  `TEXTURE_STREAMING_MAY_DISCARD`, `TEXTURE_STREAMING_NO_DEPTH_WRITE`: the feedback is a built-in pass, not a
  sampler type. Whether a custom `shader_type spatial` material feeds it is **untested until spike M1b**.
- **PR #113429** ("Implement texture mip-level streaming") merged 2026-08-27, sha `7702cddc`. Its text: feedback comes
  from *shader instrumentation* — "a material feedback buffer is bound to the shader and the used mip-level gets
  written to that buffer by materials that use a texture that is configured for streaming". `sampler2DStreamed` is
  named there as a **follow-up before release, not implemented**, "to avoid paying the cost for streaming in all
  shaders". Reading: in dev6 every spatial shader carries the instrumentation, so a custom shader sampling a
  `StreamedTexture2D` through a plain `sampler2D` should feed it. M1b confirms or refutes.
- **Forcing**: `StreamedTexture2D.max_lod_override` (1 = LOD 0, i.e. full resolution; 0 = use the global
  setting) exists per texture, and `TextureStreaming.flush_texture_streaming()` completes queued loads at once
  (signal `flush_completed`). This is the candidate for the web build's focus-first behaviour. Stall cost: M1b.
- **Spike M1b (2026-09-24, `godot/spikes/tex-stream/RESULT.md`)**, 16384×8192 Earth imported as `streamed_texture_2d`
  (BC1, 15 mips, 4.8 s import, peak RSS 2.2 GB, 89 MB on disk): a custom `shader_type spatial` with a plain `sampler2D`
  **does** stream — but the feedback value is derived from the screen-space derivative of the built-in `UV` (or of
  `STREAMING_UV` if the shader writes it), **not** from the coordinate passed to `texture()`. A shader that computes its
  own UV and never writes `STREAMING_UV` sits at 2048 forever with no warning (27.5 dB vs full res at near; verified by
  the orchestrator's re-run). Streamed pixels are bit-identical to streaming-off at far/mid/near (PSNR ∞). Resident
  size follows the camera 2048 → 4096 → 16384; the 16384 level arrives 6 frames after a hard cut. Feedback costs
  ≈ +0.03 ms GPU. A visible texture never drops on its own; a memory budget (`MemoryBudgetMbOverride`) drops it in 2 frames.
- **Forcing one texture** (the web build's focus-first): `StreamedTexture2D.MaxLodOverride = 1` +
  `TextureStreaming.FlushTextureStreaming()` brings 2048 → 16384 by the frame after `FlushCompleted`; the setter costs
  ~0.7–1 ms when the texture is small and the flush frame hitches ~45 ms. Setting an override on a texture already at
  16384 blocks 53–56 ms, so read the resident width first (`RenderingServer.TextureGetRdTexture` →
  `RenderingDevice.TextureGetFormat().Width`). `MinLodOverride` does nothing observable.
- **Decision**: GO, conditional. Use engine streaming; every planet shader writes `STREAMING_UV` unconditionally with the
  exact coordinate it samples; the memory budget is on; focus-first = `MaxLodOverride` + flush guarded by the resident
  width. Keep the 2048 LOD copies as the floor/fallback. Re-run this spike on every engine bump because PR #113429
  still plans `sampler2DStreamed`, which may change how shaders opt in.

### 3. GPU compute → render without a CPU round trip (issue #105113)
- **Claim** (report 1): BLOCKER; MultiMesh ignores GPU-written RD buffers without `multimesh_get/set_buffer`.
- **Evidence so far**: issue #105113 was **closed 2025-04-07** (label `archived`); a maintainer pointed to PR #99455,
  which added indirect drawing for MultiMesh (`multimesh_get_command_buffer_rd_rid`, present in dev6). The report's
  "BLOCKER" cites a state 17 months older than dev6. `multimesh_get_buffer_rd_rid` and `Texture2DRD` are both present. Whether #105113
  still reproduces is **untested until spike M1a**, which tries (1) compute → RD texture → `Texture2DRD` →
  vertex shader `texelFetch` by `INSTANCE_ID`, (2) compute writing the multimesh RD buffer directly,
  (3) raw draw lists.
- **Spike M1a (2026-09-24, `godot/spikes/gpu-debris/RESULT.md`)**: #105113 does **not** reproduce in dev6. Route (1)
  compute → RGBA32F RD texture → `Texture2Drd` → point mesh reading `VERTEX_ID` works; route (2) compute writing the
  MultiMesh RD buffer directly renders with no `MultimeshSetBuffer` call, even with TAA on. A frame-counter probe shows the
  draw in frame k uses frame k's compute (no one-frame lag). Raw draw lists were not needed.
- **Decision**: GO. Debris renders from GPU-resident data; route (1) is the default (0.25 ms render at 1M vs 0.81 ms and
  +64 MB for route 2). Contacts use a counting-sort grid with a 4×4×4 block-contiguous cell key (2.5× faster than a plain
  spatial hash at 1M because the 48 MB working set leaves L2).

### 4. Precision
- **Claim** (report 2): `precision=double` build for T0. (Report 1: don't.)
- **Decision (owner)**: CPU doubles in `Spayly.Sim` (no Godot reference, enforced by
  `Spayly.Sim.Tests/LayeringTests.cs`) plus a floating origin in the render layer; float32 only for camera-relative
  transforms.
- **Spike M1c (2026-09-24, `godot/spikes/scale/RESULT.md`)**: doubles in C#, `Node3D.Position` = (body − camera)/1000 km
  each frame. A 10 m cube on the moving Moon (Earth at 30 km/s) holds a projected corner to **0.0004 px max deviation**
  over 120 frames; the absolute-float control drifts **460 px**. Both re-run by the orchestrator, identical.
- **Depth cliff**: with one camera, near ≈ 7.6e-6 units (a 10 m cube 30 m away) and far ≈ 1e6–1e7 units (Neptune, the
  50 AU marker) does not z-fight — it fails outright: `ERROR: Condition "!res" is true … create_frustum_points
  (servers/rendering/rendering_light_culler.cpp:597)` and the frame goes black. Bisected: far/near = 1.3e7 renders,
  3.9e7 fails. Fix: cap far at near × 1e6 per frame (only the cube scenario needed it); the other scenarios had ratios of
  2.5–1e5. Labels: readable at cube/moon scale; Sun/Earth/Moon overlap into garbage from 30–75 AU (1.9° apart), so the
  web build's label declutter must be ported in M3.
- **Decision**: GO for a single reverse-Z camera with per-frame near/far and a hard far ≤ near × 1e6 cap; a second camera
  is not needed. A uniform-scale gotcha for M3: setting `Node3D.Basis` overwrites `Scale`; fold scale into the basis.

## Harness facts
- Verified 2026-09-24 on the spinning-cube scene (`godot/Spayly.Game`, 120 frames, Xvfb 1600×900): adapter
  `NVIDIA GeForce RTX 3080 Ti`, Vulkan 1.4.351, Forward+, X11 display server. Not llvmpipe.
- **Xvfb adds a ~37.5 ms floor to `dt_ms`** (software copy of every frame; 3 ms at 400×225). Under Xvfb only `gpu_ms`
  (viewport measured render time) and `RenderingDevice.capture_timestamp` deltas mean anything. `--windowed`
  (XWayland) has no floor: dt p50 0.37 ms on the cube.
- **The GPU lowers its clock mid-run on tiny workloads**: gpu_ms steps 0.075 → 0.62 → 1.35 ms at a random frame, so
  p50 disagreed 8× between two cube runs while min/p5 agreed within 3 %. Spike workloads must be heavy enough to hold
  the clock, and every spike reports min/p5/p50/p95. Locking clocks (`nvidia-smi -lgc`) needs root; not done.
- Screenshots of the same frame differ between runs when animation is time-based (31 dB); spikes animate by frame
  count or use `--fixed-fps` when a before/after comparison matters.
- Device limits (device.json): compute workgroup size 1024/1024/64, invocations 1024, shared memory 48 KiB,
  workgroup count X 2^31−1; max 2D texture 32768; uniform buffer 64 KiB; push constant 256 B.
- `--headless` is a dummy renderer: never used for pixels. Capture runs under `xvfb-run` with
  `--display-driver x11 --rendering-driver vulkan` (owner's choice; fallback is a windowed run on the live Wayland
  session). The run fails if the adapter is not the NVIDIA GPU. Screenshots are checked numerically by
  `godot/tools/shotcheck.py` first; a human or model looks at a PNG only when a numeric check fails.

## M3 render-side facts worth keeping
- **Depth squeeze** (`CameraRig`): near = ½ nearest surface distance, far = near × 1e6; bodies beyond near × 1e5 are pulled in along
  their own ray with radius scaled the same, so direction and angular size are exact. Render-only; sim state untouched.
- **Streaming ceiling**: `TextureStreaming.MaxLodOverride` raises the floor, it does not cap; the per-map ceiling is
  `StreamedTexture2D.MinLodOverride`, and focus-first is `MaxLodOverride` + flush guarded by the resident width. The flush frame hitches
  ~120 ms once per focus change.
- **UV**: Godot's SphereMesh UV + 0.25 maps onto three.js's convention; craters and continents line up with the web.
- **Import** of the 44 streamed maps: 30.7 s, 2.28 GB RAM peak, 914 MB on disk; `import/use_multiple_threads=false` keeps
  the 16K imports sequential.
- **Effects** follow the struck body's view each frame rather than being its children, because undo frees every view.
- **Xvfb** for correctness, `--windowed` for frame rates; frame-count waits must be scaled to the frame rate (a fly-to eases in
  real time).
- **Compositor projection** (M4): `RenderSceneData.GetCamProjection()` is Vulkan reverse-Z (depth 1 at near, 0 at far), and
  `Projection.GetZNear/GetZFar` return garbage for it (−0.576 for both). Use depth = (A z + B)/(−z) with A = `Z.Z`, B = `W.Z`:
  near = B/(A+1), far = B/A.
- **float32 in SI** (M4): gravity kernels in metres overflow in d·Q·d (~1e42) while r⁻⁷ flushes to zero; scale by 1/r first.
- **Debris stress** needs a warp: at warp 1 the sim advances too little per frame for the integrate kernel to dispatch.
